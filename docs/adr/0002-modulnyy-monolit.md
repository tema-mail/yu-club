# ADR 0002. Модульный монолит и границы модулей

Статус: принято 01.11.2026. Основа: план 3.1–3.2; ТЗ 16 §1–2, 20 §3.

## Решение

Один процесс API (`apps/api`) и один процесс фоновых задач (`worker`, тот же код, другой вход), одна база. Внутри – модули по контекстам плана 3.2.

```
apps/api/src/
  core/            time, idempotency, audit, ledger, outbox, settings, permissions, errors, db
  modules/<name>/
    index.ts       ЕДИНСТВЕННЫЙ публичный вход модуля: функции и типы для других модулей
    routes.*.ts    HTTP (public / crm)
    *.ts           внутреннее
packages/contracts/src/   Zod-схемы HTTP и событий (общие для api, site, crm)
```

Модули: `network`, `resources`, `staff`, `booking`, `clients`, `pricing`, `notifications` (Э0–Э1); `finance`, `loyalty`, `certificates`, `shifts`, `equipment`, `events`, `content`, `reports` (Э2–Э4).

## Правила границ

1. **Таблицы принадлежат одному модулю** (столбец «Владелец» в `docs/model-dannyh.md`). Писать в чужую таблицу нельзя. Читать чужую таблицу SQL-запросом нельзя – только через функцию из `modules/<x>/index.ts`. Исключение – модуль `reports` (Э4): только чтение через SQL-представления `rpt_*`, которые создаёт модуль-владелец данных (решение).
2. **Импорт** другого модуля – только `modules/<x>/index.ts`. Проверка – ESLint `no-restricted-imports` по шаблону `modules/*/!(index)` (решение). `core/*` импортируют все, `core` не импортирует модули.
3. **Синхронный вызов** – когда нужна гарантия в той же транзакции (подтверждение брони вызывает `pricing.quote`, `clients.assertCanBook`, `resources.expandToUnits`). Функции, участвующие в чужой транзакции, принимают первым аргументом `tx: Kysely<DB> | Transaction<DB>` и сами транзакцию не открывают.
4. **Асинхронно – только через outbox** (K4): событие пишется в той же транзакции, что и факт; обработчик в другом модуле – отдельная транзакция, идемпотентен. Так выполняется 16 §2.6: сбой уведомления не откатывает бронь.
5. **Команда = одна транзакция**: проверка прав (K1) → ключ идемпотентности (ADR 0004) → изменение → аудит (K2) → события (K4) → фиксация. Ответ клиенту – после фиксации.
6. **Внешние эффекты** (push, SMS) – никогда внутри транзакции команды; только из обработчика события или задачи pg-boss.
7. HTTP-слой тонкий: разбор Zod-схемы, вызов функции модуля, перевод `AppError` в ответ. Бизнес-правила в маршрутах не живут.
8. Фронт ничего не считает: остатки, доступность, статусы, цены приходят с сервера (20 §3, D-21).

## Единый тип ошибки (решение)

```ts
// apps/api/src/core/errors.ts
export class AppError extends Error {
  constructor(
    readonly code: ErrorCode,          // стабильный машинный код, см. K5 §Ошибки
    readonly httpStatus: 400 | 401 | 403 | 404 | 409 | 410 | 422 | 429 | 500 | 503,
    message: string,                   // безопасный текст для человека, по-русски
    readonly details?: Record<string, unknown>, // без ПДн чужих клиентов, без стека
  ) { super(message); }
}
```

Тело ошибки HTTP: `{ "error": { "code", "message", "details"?, "requestId" } }`. Стек и SQL – только в лог.

## Отвергнутые варианты

- Микросервисы – одна команда, общие транзакции брони/цены/клиента; распределённая транзакция дороже, чем граница по коду.
- Схема Postgres на модуль с отдельными ролями – сильнее изоляция, но 16 ролей и прав на один процесс; вернёмся, если нарушения границ появятся в ревью.
- Общий «сервисный слой» без модулей – через полгода всё пишет во всё.

## Последствия

- Каждый поток (план 5.2) работает в своём модуле и меняет чужой только через его `index.ts`.
- Изменение публичной функции модуля = изменение контракта: правится файл в `docs/kontrakty/`.
- Вынести модуль в сервис позже можно по его `index.ts` и событиям, без переписывания соседей.
