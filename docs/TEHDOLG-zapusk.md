# Техдолг для запуска в бой

Документ для команды заказчика: что сделать, чтобы вывести Ю-Клуб в бой. Код системы готов к запуску, но всё ниже требует решений, ключей, серверов или юридических текстов заказчика. Разработка это не делает: значения, которые здесь названы, – по умолчанию для стенда.

Ведётся по ходу разработки: каждый этап добавляет сюда свои пункты. Статусы: **нужно** – без этого в бой нельзя; **желательно** – можно запустить и доделать позже.

## 1. Сервер и окружение

| № | Что сделать | Статус | Как сейчас на стенде | Где в коде |
|---|---|---|---|---|
| 1.1 | Сервер в РФ (152-ФЗ, Q-90): VPS или облако, Linux, Docker Compose, от 4 ГБ RAM (на стенде 4 контейнера ≈ 250 МБ, плюс запас на Postgres и сборку) | нужно | FirstVDS 168.113.179.49, общий с другими проектами | `deploy/compose.yml`, `deploy/deploy.sh` |
| 1.2 | Домены: сайт и CRM (например `yu-club.ru` и `crm.yu-club.ru`), DNS на сервер, TTL 10 минут на время переезда | нужно | `*.168.113.179.49.nip.io` | переменные `YU_DOMAIN`, `YU_CRM_DOMAIN` в `deploy/deploy.sh`, `PUBLIC_SITE_URL` |
| 1.3 | TLS-сертификаты боевых доменов (Caddy выпускает сам по ACME); http → https кодом **301**, не 308 | нужно | `tls internal` на nip.io | `deploy/Caddyfile.yu-club`, `deploy/nginx-yu-club.conf` |
| 1.4 | `APP_ENV=prod` – включает индексацию сайта, боевой SMS-адаптер, запрещает демо-данные и тестовые коды в логе | нужно | `APP_ENV=stage` (noindex, коды входа в лог) | `apps/api/src/config.ts` |
| 1.5 | Секреты генерируются на сервере один раз и хранятся в `.env` с правами 600: пароли ролей БД, `SESSION_PEPPER`, `CERT_PEPPER`, пара `VAPID_*`. **Смена `SESSION_PEPPER` разлогинивает всех, смена `CERT_PEPPER` делает недействительными коды всех сертификатов** | нужно | создаются `deploy.sh` при первой выкладке | `deploy/deploy.sh` |
| 1.6 | `TRUSTED_PROXIES` – адреса своего обратного прокси (иначе лимиты входа считаются по одному IP на всех) | нужно | сети Docker 172.16.0.0/12 | `apps/api/src/config.ts`, `apps/crm`, `apps/site` |
| 1.7 | Перед первым выпуском – выстроить миграции 03xx/04xx в окончательный порядок (на стенде база пересоздаётся `--reset-stage`, на проде это запрещено) | нужно | `--reset-stage` | `db/migrate.ts`, план 6.5.1 |
| 1.8 | Выкладка из CI по тегу вместо ручной с мака: деплой-ключ сервера в секретах репозитория | желательно | ручная `deploy/deploy.sh` | шапка `deploy/deploy.sh` |
| 1.9 | Медиатека сайта (Э4): каталог `/opt/yu-club/media` смонтировать в контейнер Caddy **только для чтения** как `/srv/yu-club/media` (это настройка общего Caddy сервера, не репозитория); на домене CRM лимит тела 11 МБ только для маршрута загрузки медиа | нужно после Э4 | – | `deploy/Caddyfile.yu-club` (S4-07, S4-09) |

## 6. Открытые вопросы заказчику

Полный список – `docs/voprosy-zakazchiku.md`. Сейчас работа идёт по умолчаниям, записанным в `docs/reshenia.md`; перед боем каждое умолчание надо подтвердить или поменять.

## 7. Перед боем – проверки

1. Выкладка на боевой сервер с `APP_ENV=prod`, засев Владельца.
2. Сквозной e2e (`npm run test:e2e:stand` с `SITE_URL`/`CRM_URL` боевых доменов) на тестовом филиале.
3. Скилл/процедура проверки безопасности (заголовки, открытые порты, ключи) и юридическая проверка сайта.
4. Пилот на одном филиале 2–4 недели (Э5), затем остальные.
