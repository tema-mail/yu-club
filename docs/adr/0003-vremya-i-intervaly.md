# ADR 0003. Время, интервалы, зона филиала

Статус: принято 01.11.2026. Основа: 01 §3, §4, §4.1; 02 §6.4 (план 3.3); 09 §6.1, §13; 16 §2.4; Q-83.

## Решение

1. **Хранение.** Все моменты – `timestamptz` (UTC). Процессы и контейнеры – `TZ=UTC`. Локальное время в базе не хранится, кроме «настенных» значений графика (`time`, `date` – часы работы, дата исключения), у которых зона берётся из филиала.
2. **Зона.** У города – зона по умолчанию, у филиала – своя IANA-зона (`Europe/Moscow`, `Asia/Novosibirsk`), по умолчанию наследуется от города (15 §5.2). Проверка имени зоны – в приложении при сохранении: `new Intl.DateTimeFormat('ru', { timeZone })` не бросает `RangeError` (функция `isValidTimeZone`, K8).
3. **Интервалы.** Только полуоткрытые `[начало, конец)` (01 §3): в Postgres `tstzrange(start, end, '[)')`, в TypeScript `Interval { start: Date; end: Date }`, `start < end`. Пересечение – оператор `&&`; соседние слоты `[14:00,14:30)` и `[14:30,15:00)` не пересекаются.
4. **Сутки филиала** – `[локальная полночь даты, локальная полночь следующей даты)` по зоне филиала. Окно записи, «сегодня», отчёты по дням – только через эти функции. Сетевой отчёт – сумма локальных суток филиалов (Q-83).
5. **Выравнивание слота** – относительно локальной полуночи филиала: начало и длительность кратны шагу типа ресурса (VR 15, ПК/PS 30 – 01 §4). Длительность ≥ одного шага (R-02 по умолчанию).
6. **Через полночь – нет** (01 §4.1): `close_time > open_time`, интервал брони не пересекает локальную полночь. Ограничение CHECK в графике и проверка в K5.
7. **Неоднозначное локальное время** (переход на летнее время в тестовой зоне): `disambiguation: 'compatible'` – несуществующее время сдвигается вперёд, двойное берётся раньшее. В зонах РФ переходов нет, правило нужно для теста и будущих филиалов вне РФ (09 §13).
8. **Смена зоны филиала не сдвигает прошлое**: моменты хранятся в UTC, а версия брони хранит снимок `branch_timezone` (решение). Отображение старой брони – по снимку; новые – по текущей зоне. Смену зоны при наличии будущих броней CRM показывает как «затронутые записи» (01 §4.1 п.5).
9. **Библиотека** – встроенный `Temporal` Node 26 (ADR 0001), только внутри `core/time.ts`. Остальной код получает `Date` и брендированные строки `LocalDate` (`YYYY-MM-DD`), `LocalTime` (`HH:mm`). Прямое `new Date().getHours()`, `toLocaleString` без зоны и `date-fns` в коде модулей запрещены (ESLint `no-restricted-syntax` по `getHours|getDate|setHours`, решение).
10. **«Сейчас» – один источник: `Clock`** (`core/time.ts`, `interface Clock { now(): Date }`). Команда берёт `const now = clock.now()` один раз в начале и передаёт его в SQL параметром `$now` – для `expires_at` удержаний и ключей идемпотентности, `hold_expires_at <= $now` при гашении, `occurred_at` аудита и событий, `planned_at` уведомлений. SQL-функция `now()` в командах и их условиях не используется (решение по ревью: иначе тест с `fixedClock` и база расходятся, а `now()` в Postgres – время начала транзакции, не момент проверки). `DEFAULT now()` допустим только у технических `created_at`/`recorded_at`.

## Почему

- `tstzrange` + `EXCLUDE USING gist` даёт защиту от пересечений в самой базе (ADR 0004, K6).
- Хранение UTC + снимок зоны делает смену зоны безопасной и не требует миграции данных.
- Один модуль времени ловится тестами на чужой `TZ` машины (план 8).

## Отвергнуто

- Хранить локальное время брони + зону – сравнения между филиалами и пересечения клиента по сети (01 §9 п.5) усложняются.
- `timestamp without time zone` – ошибка при первом филиале в другой зоне.
- Закрытые интервалы `[a, b]` – соседние слоты конфликтуют.

## Последствия

- Все функции времени – в K8, тесты S0-04 обязательны до первого использования в модулях.
- Для гонки за «21:00 накануне» и «−15 мин» планировщик хранит плановый момент UTC, вычисленный в момент постановки, и пересчитывает его при переносе (09 §6.4).
