## 1. Главное правило: только чтение через представления `rpt_*`

Как в `reconcile.ts` и миграции 0211: `reports` не читает чужие таблицы напрямую, а только представления `app.rpt_*`, которые **принадлежат модулю-владельцу данных** (формулу меняет только владелец, шапка миграции называет владельца каждого представления). Права: у `yu_app` на `rpt_*` только `SELECT` (`REVOKE INSERT, UPDATE, DELETE, TRUNCATE`, как 0211); пул отчётов ходит под отдельной ролью `yu_reports` (§9). Плановое доступное время – единственное исключение: оно считается пакетным вызовом `network.openIntervalsRange` (новый, S4-59: диапазон дат, та же `resolveDay`, что у `openIntervalsBulk` в `apps/api/src/modules/network/calendar.ts:205`, одна транзакция и одна загрузка графика на диапазон) – это источник истины расписания с приоритетом ресурс → комната → филиал → регулярный; дублировать его в SQL – две реализации одного правила (решение). Отчёты свои факты не создают (14 §2.1); кэш – только для повторного показа, источник – первичка.

## 2. Общие правила расчёта (14 §2)

**Период.** Быстрые периоды 14 §2.2 и произвольный; обе даты включительно. Период задаётся **локальными датами**; для филиала – интервал UTC `[branchDay(from).start, branchDay(to).end)` по его зоне (K8 `branchDay`, `core/time.ts:134`); для сети и города – сумма по филиалам, каждый по своим суткам (Q-83, по умолчанию, ждёт заказчика). На экране и в файле подпись: «Сутки – по времени каждого филиала».

**Дата события, а не создания** (14 §2.2, приёмка 3): у каждого показателя – поле `dateBasis` (`session_start`, `created_at`, `arrived_at`, `occurred_at`, `marked_at`, `at`), показывается в подписи («по дате сеанса»).

**Сравнение** (14 §4.2): произвольный период – с предшествующим той же длины; календарный месяц – с прошлым календарным месяцем; неделя – с прошлой неделей. Процент не считается при базе 0 – `deltaPct: null`, показывается «–» (14 §2.4, приёмка 22). Сравнение с прошлым годом – нет (Q-142).

**Значение показателя:**
```ts
type Metric =
  | { state: 'ok'; value: number; unit: 'count' | 'kop' | 'centi' | 'minutes' | 'pct'; prev?: number | null; deltaAbs?: number | null; deltaPct?: number | null }
  | { state: 'no_data' }                                   // за период нет записей
  | { state: 'unavailable'; reason: 'source_not_ready' | 'missing_input' | 'not_permitted' }; // нельзя посчитать
```
0, «нет данных» и «недоступно» не смешиваются (приёмка 21): `0` – записи есть, сумма 0; `no_data` – записей нет; `unavailable` – источника нет (Э3 не выпущен → `source_not_ready`), нет данных для формулы (ремонт без даты начала → `missing_input`, 14 §13), нет права на часть (`not_permitted`). Отсутствующая себестоимость – не 0.

**Деньги не смешиваются** (14 §4.3, приёмка 7, 24): стоимость броней, поступления, возвраты, расходы, движение, остаток – разные показатели; «прибыль» в подписях не используется; баллы – в `centi`, рядом с деньгами не складываются.

**Детализация = итог** (14 §15, приёмка 17–18; TC-20): у каждого показателя есть `detail` – список исходных строк с теми же фильтрами и условием сегмента; агрегат и детализация строятся **одним** построителем условия (`framework.ts: where(spec)`), сумма строк детализации совпадает с агрегатом при тех же правилах округления (копейки целые, баллы – сотые; доли и проценты округляются только при показе, до 0,1). Тест-свойство S4-62: для случайных фильтров `Σ detail = aggregate`.

**Актуальность** (14 §2.4, приёмка 20): отчёты считаются по живой базе в момент запроса – `computedAt` в ответе; при ошибке расчёта показывается ошибка, а не прошлый результат (кэша результатов на сервере нет – решение; если S4-131 покажет > 5 с – вводятся дневные агрегаты `report_daily_*` со своим `refreshedAt`, отдельной правкой контракта).

### 3.1. Сводный дашборд (14 §4) – `dashboard.ts`

### 3.2. Бронирования и посещаемость (14 §5) – `bookings.ts`

| Показатель | Формула | `dateBasis` |
|---|---|---|
| создано бронирований | `count(B) где created_at ∈ P` | `created_at` |
| запланировано сеансов | `count(B) где start ∈ P и status ∉ (cancelled_*)` | `session_start` |
| состоялось посещений | `count(rpt_visits) где planned_start ∈ P` | `session_start` |
| отменено клиентом / клубом | `count(B) где status = cancelled_by_client / cancelled_by_club и start ∈ P`; инициатор – из статуса | `session_start` (решение: отмена относится к сеансу; `cancelled_at` – колонка детализации) |
| перенесено | `count(DISTINCT booking_id) из rpt_booking_reschedules где rescheduled_at ∈ P` | `rescheduled_at` |
| неявки | `count(rpt_no_shows) где planned_start ∈ P` – только явно отмеченные (14 §5.2) | `session_start` |
| ожидают решения | `count(B) где needs_decision` (прошедшие `confirmed` без отметки, R-08; K11 №3) – на конец периода | момент запроса |
| средняя длительность состоявшегося | `avg(planned_minutes)` посещений периода (Q-40: время – по расписанию; фактического времени нет) – подпись «по расписанию» | `session_start` |
| уникальные идентифицированные посетители | `count(DISTINCT client_id)` посещений, где `client_kind = 'profile'`; брони без профиля – в «состоялось», но не здесь (14 §5.2, приёмка 12) | `session_start` |

Детализация (14 §5.3): дата и время по филиалу, филиал, клиент (маска §6), ресурс, длительность, статус, стоимость, оплата (из `rpt_payments`: оплачено/способ/не оплачено), причина отмены или неявки, переход в карточку брони. Фильтры: период, город, филиал, статус, тип ресурса (ПК/VR/PlayStation/комната целиком), клиент, инициатор отмены, администратор (кто создал/отметил), наличие оплаты.

### 3.3. Загрузка ресурсов (14 §6) – `utilization.ts`

Считается **по единице занятости** (`rpt_units`, только `self_bookable` ресурсы и единицы VR), минуты – целые, все интервалы – `tstzmultirange` (PostgreSQL 16: `range_agg` склеивает пересечения – двойного счёта нет, 14 §6.2, приёмка 6).

| Показатель | Формула (на единицу, затем сумма по выбранным) |
|---|---|
| плановое доступное время `A` | `Σ` открытых интервалов `network.openIntervalsRange` за период (по каждому дню – та же `resolveDay`; закрытия и исключения уже вычтены) для ресурса единицы, пересечённых с `P`; один вызов на филиал, не на день – иначе месяц × 20 филиалов даёт сотни запросов к календарю |
| время блокировок `L` | `range_agg(rpt_unit_blocks.period) * A` – только внутри доступного времени (приёмка 6 «без двойного вычета») |
| технический простой | часть `L` с `kind ∈ (repair, maintenance)` |
| забронированное `Bk` | `range_agg(rpt_unit_booked.period) * A` |
| фактически использованное `F` | `range_agg(period броней с живым посещением) * A` (неявка – не использование, 14 §6.2) |
| свободное | `A − (Bk + L)` в мультидиапазонах: `A − range_agg(Bk ∪ L)` |
| фактическая загрузка | `F / A × 100%`; `A = 0` → `unavailable/missing_input` |
| коммерческая занятость | `Bk / A × 100%` – отдельной колонкой с подписью «не равна фактической: бронь может закончиться неявкой» |

Решение: блокировки вычитаются из числителя «свободного», а не из `A`: 14 §6.2 определяет `A` по расписанию филиала без блокировок, иначе ремонт поднимал бы загрузку.

**Комната VR+PS4** (14 §6.3, K6): строки по VR1 и VR2 отдельно; PS4 (`self_bookable = false`) в загрузку не входит; аренда комнаты целиком (`whole_room`) занимает обе единицы и показывается **дополнительной строкой** «Аренда комнаты целиком: N броней, M минут» без сложения с VR1 + VR2. Итог по филиалу – сумма по единицам с подписью «единица = место».

Представления: таблица по филиалам и ресурсам; график по дням и по часам (часы – по зоне филиала, разбиение мультидиапазонов по часовым ячейкам); детализация – календарь единицы с бронями, свободными интервалами и блокировками. Сетевой график по часам – только при одной зоне в выборке, иначе «по местному времени каждого филиала» (Q-83).

### 3.4. Финансы и касса (14 §7) – `finance.ts`

Согласуется с финсводкой K17 §9 (`finance/summary.ts`, Э2): те же определения, отчёт – расширение на период, город, сеть и детализацию (решение: одна формула, сводка K17 §9 переходит на `rpt_finance_operations` в S4-65, тесты Э2 остаются зелёными).

| Показатель | Формула по `rpt_finance_operations` за `occurred_at ∈ P` |
|---|---|
| поступления (всего и по источнику `session`, `event`, `certificate_sale`, `extra_service`, `other`) | `Σ signed_kop` где `original_kind = 'income'` (сторно входит со знаком минус в свою же строку источника) |
| возвраты | `Σ amount` где `original_kind = 'refund'` (с учётом сторно); возврат не удаляет поступление (14 §7.2) |
| расходы по категориям (2 уровня) | `Σ amount` где `original_kind = 'expense'`, группировка `category_id → subcategory_id` |
| изъятия, перемещения, корректировки | отдельные строки, в «чистое движение» не входят: изъятие – выход денег из кассы, но не расход (K17 §4); показываются в «Остаток» |
| чистое движение | `Поступления − Возвраты − Расходы` (14 §7.2) |
| остаток на начало / конец | по каждому месту денег (наличные, безнал, K17 §2): `остаток(t) = Σ signed_kop всех операций до t` (включая `opening_balance`); конец = начало + поступления − возвраты − расходы ± изъятия, перемещения, корректировки (14 §7.2) – сверяется тестом |
| по способам оплаты | группировка `method`: наличные, карта, перевод (14 §7.3); баллы и сертификаты – **не** деньги: отдельный блок «Неденежная оплата сеансов» из `rpt_payments` (`points`, `certificate`) |

Представления 14 §7.4: движение денег; остаток на дату; структура поступлений; структура расходов; финансовый результат мероприятий (после Э3, §3.5); продажи и погашения сертификатов (ссылка на 3.8). Детализация – таблица операций 14 §7.4 с переходом к первичному объекту (`ref_type/ref_id`).

### 3.5. Мероприятия (14 §8) – `events.ts`, **ждёт K20**

Источник – `rpt_events` и `rpt_event_money` из 0311 (K20 §11): строка мероприятия `event_id, branch_id, status, held_on (дата проведения по зоне филиала), agreed_price_kop, planned_cost_kop, planned_cost_by_kind, has_booking`; движение денег – **из `rpt_event_money`** (связи K17 §14: поступления, возвраты, расходы со статьёй – аниматор, кейтеринг, продукты, декор, подрядчики, прочее), а **не** из `rpt_finance_operations` по `ref_type = 'event'`: расход, привязанный вручную (`linkOperation`), своего `ref_type` не имеет и выпал бы из факта. Формулы 14 §8.2: отклонение = факт − план себестоимости; результат = поступления − возвраты − факт. прямые расходы; остаток к оплате = согласованная стоимость − (поступления − возвраты, восстанавливающие долг по классификации возврата). Период – по дате проведения, деньги мероприятия – все операции мероприятия независимо от их даты (решение по разбору 13–16, дыра 6: иначе предоплата прошлого месяца выпадает из результата); подпись «деньги – за всё время мероприятия». Мероприятия без брони включаются (приёмка 10).

### 3.6. Клиенты и повторные посещения (14 §9) – `clients.ts`

| Показатель | Формула |
|---|---|
| новые профили | `count(rpt_clients) где created_at ∈ P и status ≠ 'guest'` (новый профиль ≠ первый визит) |
| клиенты с посещением | `count(DISTINCT client_id)` посещений периода, профиль |
| впервые пришедшие | клиенты, у которых **первое** посещение за всю историю ∈ P |
| вернувшиеся | клиенты с посещением в P и посещением **до** P |
| повторные посетители | `≥ 2` посещений за всю историю и хотя бы одно ∈ P (14 §9) |
| посещений на клиента | посещения профилей в P / клиенты с посещением |
| средний интервал между посещениями | среднее по клиентам с ≥ 2 посещениями в P разниц соседних `planned_start` (дни) |
| не посещавшие в периоде | клиенты с посещением до P и без посещения в P |
| по филиалам | те же показатели по филиалу посещения; один клиент может быть в нескольких филиалах – итог сети не равен сумме (подпись) |

Брони без профиля (`guest`) – только в общей посещаемости 3.2 (14 §9, Q-14 §19 п.12). Детализация – обезличена по умолчанию (§6).

### 3.7. Лояльность и баллы (14 §10) – `loyalty.ts`

По `rpt_loyalty_moves` за `at ∈ P` (сотые балла): начислено (`accrual`), списано на время (`spend` по сеансам) и на товары (`spend` по товарам, K15 §6), штрафы (`penalty`), возвраты в партии (`return`), ручные корректировки, сгорание (`expire`, при `batch_ttl_days`); сторно – в строку исходного типа со знаком минус. На конец периода (из `rpt_loyalty_balances` на момент запроса; на прошлую дату – `Σ` записей до даты): клиенты с положительным и отрицательным балансом, на пороге блокировки (`−50 < баланс ≤ −45` – по умолчанию, порог в подписи, ждёт заказчика Q-80), заблокированные (`≤ −50`), общий объём. Правила 07 отчёт не пересчитывает – только показывает факт операций. Баллы не входят в денежную выручку (приёмка 9).

### 3.8. Сертификаты (14 §11) – `certificates.ts`

По `rpt_certificate_ops`: продажи (шт., сумма) – по филиалу продажи; погашения (сумма, по филиалу погашения – взаиморасчёт Q-25); частично погашенные (остаток > 0 и были погашения); истёкшие и сумма сгоревших остатков; аннулированные; на конец периода – активные и их остаток. Продажа – поступление (уже в 3.4 как `certificate_sale`), погашение – не поступление (приёмка 8). Подарок имениннику – отдельный раздел «Права на услугу» из `rpt_events` (K20) – до Э3 `unavailable/source_not_ready` (приёмка 14). Детализация погашения: дата, сумма, клиент (маска), сеанс, сотрудник, остаток после (14 §11).

### 3.9. Сотрудники и смены (14 §12) – `staff.ts`, **ждёт K18**

Требования к `rpt_shifts`/`rpt_payroll`: смена `shift_id, branch_id, staff_id, planned_period, actual_period, state ('planned'|'open'|'closed'|'empty'|'unclosed')`, расчёт `period, staff_id, hours_amount_kop, per_shift_kop, penalties_kop, adjustments_kop, to_pay_kop, paid_kop, paid_at`. Показатели 14 §12; пустая (нет сотрудника) и незакрытая (не завершена) – разные строки (приёмка 15); правило ставки за короткую смену – из настроек K18, отчёт его не предполагает. Денежные колонки – только `reports.payroll.view` (§8): у Директора оно есть в своей зоне (как `payroll.view` Э3, решение техлида 04.11); у Администратора – `unavailable/not_permitted`.

### 3.10. Оборудование и ремонты (14 §13) – `equipment.ts`, **ждёт K19**

Требования к `rpt_equipment`/`rpt_repairs`: единица `equipment_id, branch_id, resource_ids, status (единый список Q-50), inventory_no, serial_no`; ремонт `repair_id, equipment_id, started_at | null, finished_at | null, contractor_id, warranty boolean, incident_at`; расходы – из `rpt_repair_money` (0311, связи K17 §14), не по `ref_type = 'repair'`: вручную привязанный расход иначе выпадает (без двойного учёта, 14 §13). Простой – `range_agg` блокировок вида `repair` по ресурсам единицы (как 3.3); длительность ремонта без `started_at` – `unavailable/missing_input` (14 §13); повторные поломки – ≥ 2 инцидентов одной единицы за 90 дней (по умолчанию, порог в подписи).

### 3.11. Уведомления и публикации (14 §14) – `comms.ts`

По `rpt_notifications`, раздельно по категориям `service` / `reminder` / `marketing`: создано, передано провайдеру (`sent_to_provider`, подпись «передано в браузер, показ не подтверждён» – 14 §14), только в центре (`no_channel`, `inbox_only`), пропущено по настройкам, по частоте, из-за изменения брони, ошибки; рекламные кампании – число и охват; отказы от рекламы (`rpt_consent_changes`, `granted = false`); опубликованные материалы по типам (`rpt_content_versions`, первая публикация в P). Прочтения в центре – отдельный показатель «открыто в кабинете» (по `read_at`, достоверное событие нашего канала). ## 7. Экспорт CSV и XLSX (14 §16; 17 §4.3; Q-80)

Форматы – XLSX и CSV (по умолчанию, ждёт заказчика Q-80); PDF – не в Э4 (Q-140).

**Задача** (`export.ts`, таблица `report_exports`, pg-boss `reports:export`):

```
queued → running → ready → expired
queued|running → failed (error_code)
```
`requestExport(ctx, { report, params, format, detail: boolean })` – права §8 проверяются при постановке **и** при скачивании; `params` – те же фильтры, что на экране, нормализованные; `params_hash` = SHA-256 нормализованных параметров + `staff_id` + `format`; повтор того же запроса, пока прежняя задача `queued/running/ready`, возвращает её (идемпотентность по `UNIQUE (staff_id, params_hash) WHERE status IN ('queued','running','ready')`), плюс `Idempotency-Key` на маршруте.

**Файл:**
- заголовок (14 §16): название отчёта, период и правило суток, дата и время формирования (зона – филиала, для сети – Москва с подписью), фильтры словами, область (город/филиал), итоговые показатели, пояснение формул и единиц (копейки → рубли с двумя знаками, баллы – с двумя знаками);
- CSV – UTF-8 с BOM, разделитель `;` (Excel в русской локали – решение), RFC 4180 кавычки, `\r\n`;
- XLSX – потоковая запись (`exceljs` `WorkbookWriter`), лист «Данные» и лист «Параметры», числа – числами, даты – датами в зоне филиала. Перед подключением `exceljs` – аудит пакета и его зависимостей (`npm audit`, давность выпусков, сопровождение); не прошёл – запасной вариант: только CSV или свой потоковый XLSX (zip-поток + XML листа, без библиотеки);
- **защита от формул** (CSV/XLSX injection): **текстовая** ячейка, начинающаяся с `=`, `+`, `-`, `@`, `\t`, `\r`, получает префикс `'`; числа и даты не трогаются (`-150,00` остаётся числом, иначе ломаются суммы в Excel); в XLSX все строки пишутся как строки, не как формулы;
- маскировка – §6 по правам **постановщика**;
- лимит – 200 000 строк (больше → `EXPORT_TOO_LARGE`, просьба сузить период).

**Хранение:** `EXPORT_DIR` (`/opt/yu-club/exports`, вне веб-корня, Caddy его не отдаёт), имя – случайный UUID; срок 24 ч (`reports.export_ttl_hours`), затем файл удаляется задачей `reports:export-gc`, строка → `expired` (Q-145). Скачивание – только автор задачи через K11 №246 с проверкой прав в момент скачивания, `Content-Disposition: attachment`, `Cache-Control: no-store`. В бэкап экспорт не входит (временные ПДн).

**Аудит:** `export.requested` (отчёт, фильтры, формат, `detail`, маска да/нет), `export.downloaded`, `export.failed` (K2, тип объекта `export` – есть). Экспорт с ПДн, зарплатой или детальными финансами – отдельное право (§8) и аудит (14 §16, приёмка 23).

## 12. Сверка 16 §14 (дополняет `reconcile.ts`)

В Э4 – без новых проверок денег (S2-80 их уже делает). Сверки по сущностям Э3 («расходы мероприятия = связанные операции», «начисление воспроизводится») делает Э3 – S3-95 (S4-134 снят, решение техлида 04.11). Э4 добавляет одну проверку – шаг S4-136 после S4-64: «фактическое время загрузки ≤ доступного планового» по каждой единице за прошлые сутки (расхождение = бронь вне расписания, `discrepancy` с `check_name = 'utilization_over_capacity'`). CHECK `check_name` расширяют 0311 и 0408: каждая делает `DROP CONSTRAINT` + `ADD CONSTRAINT` с полным списком значений на свой момент, поэтому применённая позже содержит всё.
