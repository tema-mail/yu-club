# ADR 0004. Журнал операций со сторно и идемпотентность команд

Статус: принято 01.11.2026. Основа: план 3.3; ТЗ 06 §4.4, 07 §3.2–3.3, §8.4, 08 §3.3, 16 §2.2, §2.7, §15.2–15.3, 17 §9.

## 1. Журнал операций (ledger)

**Решение.** Один механизм для кассы филиала, бонусного счёта клиента, остатка сертификата и расчёта сотрудника (вывод разбора 05–08, строка «Журнал операций со сторно»).

- `ledger_accounts` – счёт: вид, единица, филиал, владелец, **кэш баланса** `balance` и нижняя граница `min_balance`.
- `ledger_entries` – запись: сумма со знаком (целое в минорных единицах), тип, основание, ссылки, автор, `reversal_of`, `idempotency_key`, `posting_id`. Таблица **только на вставку** (роль `yu_app` без UPDATE/DELETE).
- **Проводка** (`posting`) – одна или несколько записей с общим `posting_id`, вставляются одной транзакцией (перевод между кассами = две записи).
- **Баланс** пишет только база: триггер `ledger_entries_20_apply_balance` (BEFORE INSERT, SECURITY DEFINER) блокирует строку счёта `FOR UPDATE`, считает новый баланс, проверяет нижнюю границу (сертификат – 0, баллы – −50, 07 §3.1; касса – `NULL` или 0 по настройке Э2), ставит `balance_after` и обновляет `balance`. У `yu_app` нет UPDATE на `ledger_accounts` (кроме `status`) – обойти журнал нельзя. Уход ниже границы допустим только явным режимом `limit_override` (право + причина от сотрудника, K3). Инвариант «`balance` = сумма записей» проверяет тест и ночная сверка (16 §14).
- **Единицы (решение, отступ от плана 3.4):** все суммы – `bigint` в минорных единицах: `RUB_KOP` (копейки), `POINT_CENTI` (сотые балла: 2,5 балла = 250). Точность та же, что `numeric(12,2)`, но одна целочисленная арифметика в TS (`Number.isSafeInteger`) и SQL. Показ баллов – 1 знак (Q-41).
- **Сторно** – новая запись: тот же счёт, сумма `= −исходной`, `reversal_of = id исходной`, причина обязательна. `UNIQUE(reversal_of)` – второе сторно той же записи невозможно. Сторно сторно запрещено (триггер `ledger_entries_10_check_reversal` – единственное имя); повторное исправление – новой обычной операцией.
- **Партии баллов** (07 §3.2) и резервы – таблицы модуля `loyalty` поверх журнала (Э2), ссылаются на `ledger_entries.id`; в журнал не встраиваются.

**Отвергнуто:** баланс только как `SUM()` без кэша – нечем держать нижнюю границу в базе при гонке двух списаний; отдельные журналы на каждый модуль – четыре реализации сторно и идемпотентности; `numeric` для денег – допустимо, но смешанная арифметика в JS (`string`/`number`) опаснее.

## 2. Идемпотентность команд

**Решение.** Каждая изменяющая команда из 16 §15.2 (удержание, добавление слота, подтверждение, отмена, перенос, приход, неявка, оплата, возврат, погашение, операции баллов, ручная отправка уведомления) принимает заголовок `Idempotency-Key` (UUID, генерирует клиент один раз на намерение – на нажатие кнопки, а не на попытку).

Механизм – захват ключа **в той же транзакции**, что и команда:

```sql
INSERT INTO idempotency_keys (scope, key, request_hash, created_at, expires_at)
VALUES ($scope, $key, $hash, $now, $now + interval '72 hours')   -- $now из Clock (ADR 0003 п.10)
ON CONFLICT (scope, key) DO NOTHING
RETURNING key;
```

| Ситуация | Поведение |
|---|---|
| строка вставлена | выполняем команду; перед фиксацией пишем `response_status`, `response_body`; фиксируем всё вместе |
| параллельный дубль, первая транзакция ещё идёт | `INSERT` второй ждёт уникальный индекс; после фиксации первой `ON CONFLICT` → читаем сохранённый ответ и отдаём его (тот же статус, тело, заголовок `Idempotent-Replay: true`) |
| первая откатилась (ошибка, отказ по правилу) | ключ не сохранён, вторая выполняется заново – эффекта не было, повтор безопасен |
| ключ есть, `request_hash` другой | `409 IDEMPOTENCY_KEY_REUSED`, команда не выполняется |
| ключ старше `expires_at` | ключ удаляется задачей очистки; для денег и баллов вторая линия – `UNIQUE(ledger_entries.idempotency_key)` навсегда |

- `scope` = `<тип актора>:<id актора>:<операция>`, например `client:…:booking.confirm`, `visitor:…:hold.create`, `staff:…:booking.cancel`. Ключи разных акторов не пересекаются.
- `request_hash` = SHA-256 канонического JSON (сортировка ключей) от `{route, params, body}`.
- Отказы по бизнес-правилам **не сохраняются** – ошибка откатывает транзакцию вместе с ключом (решение: отказ «слот занят» не должен навсегда закрепляться за ключом, слот может освободиться).
- Без заголовка команды из 16 §15.2 получают `400 IDEMPOTENCY_KEY_REQUIRED` (решение: не генерируем ключ на сервере – иначе повтор после обрыва создаст дубль).
- Двойной клик в UI дополнительно гасится блокировкой кнопки, но защиту даёт сервер.

**Неизвестный исход внешнего эффекта** (push, SMS): обработчик фиксирует попытку до вызова провайдера (`status = 'sending'`), после ответа – результат. Тайм-аут = `unknown`, повтор только по политике K4/K9 и с тем же ключом провайдера, если он есть. Повтор «вслепую» денежных и бонусных эффектов запрещён: сначала поиск исходной операции по `idempotency_key` (16 §15.3).

## 3. Повтор транзакции при взаимоблокировке (решение по ревью)

Команды занятия пишут все строки одним `INSERT ... SELECT ... ORDER BY unit_id` и блокируют единицы в порядке `id` (K6) – это убирает большинство взаимоблокировок. Если всё же `40P01` (deadlock) или `40001` (serialization) – команда повторяется **один раз** целиком (новая транзакция, тот же ключ идемпотентности, тот же `$now`); вторая неудача → `409 SLOT_HELD` («время сейчас оформляет другой гость»). Тест «50 параллельных подтверждений» гоняется на пуле ≥ 50 соединений, иначе он проверяет очередь пула, а не базу.

## 4. Outbox

Событие пишется в `outbox_events` той же транзакцией, что и факт. Диспетчер (pg-boss, раз в 1 с и по `NOTIFY outbox`) ставит задачу на каждого подписчика с `singletonKey = <eventId>:<handler>`. Обработчик в своей транзакции вставляет `processed_events(handler, event_id)` – повторная доставка ловится PK и ничего не делает. Повторы – экспоненциально, до 10 попыток, затем `failed` и запись в журнал ошибок (контракт – K4).

## Последствия

- Тесты S0-05/S0-07/S0-08: 20 параллельных одинаковых запросов → одна запись; тот же ключ с другим телом → 409; сторно дважды → ошибка базы; обработчик дважды → один эффект.
- Таблица ключей растёт – очистка задачей раз в час (`DELETE ... WHERE expires_at < $now`, задача берёт $now из Clock).
