# План выкладки и отката

По ТЗ 17 §17 (развёртывание и обновление), 18 §9.2 п.17 и §15 (план отката для релизов, затрагивающих данные). Источник шагов – `deploy/deploy.sh`, `deploy/compose.yml`, `db/migrate.ts`, `docs/adr/0001-stek.md`. Снимок на 11.11.2026.

## 1. Что выкладывается и чем

Один скрипт `deploy/deploy.sh` с мака (или с машины с ssh-доступом к серверу): код из `git HEAD` → `$ROOT/src` на сервере, сборка образов `api`, `crm`, `site` (CRM и сайт собираются локально, `dist` отправляется), Postgres 16, миграции под `yu_owner`, запуск `api`, `worker`, `crm`, `site`, свой блок в общем Caddy, 301 http → https через nginx, cron бэкапа, проверка снаружи. Переменные: `YU_HOST`, `YU_KEY`, `YU_DOMAIN`, `YU_CRM_DOMAIN`, `YU_ROOT`, `YU_CADDY`, `YU_CADDY_CT`, `YU_CADDY_NETWORK`, `YU_NGINX_CONF`, `YU_NEIGHBOURS` (шапка скрипта).

Образы помечены `yu-club-api:local`, `yu-club-crm:local`, `yu-club-site:local` без версии; версия кода – `GIT_SHA` в образе API и `$ROOT/src/REVISION`, её отдаёт `/health`. Предыдущий код сервер хранит в `$ROOT/src.old` (одна версия назад), образы старой сборки удаляет `docker image prune` в конце выкладки. Выкладка из CI по тегу не сделана (техдолг 1.8).

## 2. До выкладки

1. Ветка `main`, рабочее дерево чистое по `apps db deploy package.json package-lock.json .dockerignore` – иначе `deploy.sh` откажет.
2. CI зелёный на этом коммите (`.github/workflows/ci.yml`: typecheck, lint, сборка CRM и сайта, тесты бэкенда на Postgres, Playwright CRM и сайта).
3. Список изменений релиза (18 §15): реализованные требования, изменения для пользователя, известные дефекты, **список миграций релиза с пометкой «совместима со старым кодом: да/нет»** (п. 6).
4. Бэкап до выкладки, вручную, и проверка: на сервере `$ROOT/backup.sh && $ROOT/restore-check.sh`; строка «восстановление … проверено» в `$ROOT/backups/backup.log`. Имя дампа – в запись о релизе: к нему откатываемся.
5. Сотрудники предупреждены о работах, если выкладка затрагивает доступность (17 §17 п.5): выкладка перезапускает контейнеры, CRM недоступна минуту-две, открытые сессии сохраняются (`SESSION_PEPPER` не меняется).
6. Окно: вне часов пик филиалов; не в ночь бэкапа 04:40 UTC.
7. Копия вне сервера за прошлую ночь на месте (`offsite-pull.sh`, журнал `~/Backups/yu-club/logs/offsite.log`).

## 3. Порядок выкладки

```bash
# стенд (значения по умолчанию из скрипта):
deploy/deploy.sh
# бой (пример):
YU_HOST=root@<ip> YU_KEY=~/.ssh/<ключ> YU_DOMAIN=<сайт> YU_CRM_DOMAIN=<crm> \
  YU_CADDY=/etc/caddy/Caddyfile YU_CADDY_CT=caddy YU_CADDY_NETWORK=caddy YU_NGINX_CONF=none deploy/deploy.sh
```

Что делает скрипт по шагам (нумерация как в файле):

1. Код: `git archive HEAD` → `$ROOT/src.new` → перестановка `src` → `src.old`; каталоги `data`, `backups`, `attachments`, `media`, `exports` с правами; `REVISION`. Сборка `dist` CRM и сайта на маке и отправка.
2. Окружение: `$ROOT/.env` (600) создаётся один раз с паролями ролей БД; недостающие секреты (`SESSION_PEPPER`, `CERT_PEPPER`, `PREVIEW_SECRET`, `VAPID_*`, `YU_BOSS_PASSWORD`, `YU_REPORTS_PASSWORD`) дописываются один раз. Существующие значения не трогаются.
3. На сервере: сборка образов по одному (`build --pull -q`), `up -d --wait postgres`, роли `yu_boss` и `yu_reports`, миграции `run --rm -T migrate` (`node db/migrate.ts up`), схема `pgboss`, `up -d --wait api crm site`, `up -d worker`, проверка, что worker запустился и написал «запущен», уборка старых образов.
4. Caddy: вырезается прежний блок `# >>> yu-club … # <<< yu-club`, дописывается новый с заменой доменов, `caddy validate`, при ошибке – возврат копии, иначе `caddy reload`. Коды ответов соседних сайтов снимаются до и после; изменились – предупреждение.
5. nginx (если `YU_NGINX_CONF` не `none`): файл 301 в `conf.d`, `nginx -t`, reload, при ошибке – возврат.
6. cron: `$ROOT/backup.sh` и `$ROOT/restore-check.sh` в `/etc/cron.d/yu-club` на 04:40 UTC.
7. Снаружи: `/health` (код и версия), `http://…/health` → 301, сайт `/`, CRM `/login`, медиатека `/media/<файл>`. Последняя строка «→ готово … (ревизия <sha>)»; если `/health` не отдал версию – код выхода 1.

`--reset-stage` – только стенд: скрипт дважды проверяет `APP_ENV=stage` в `.env` и отказывает иначе. Делает бэкап, пересоздаёт базу, миграции с нуля, `deploy/seed-stand.sh` (Владелец и демо-данные). На бою запрещено: демо-засев сам отказывает при `APP_ENV=prod`.

## 4. Проверки после выкладки

Автоматические – в конце `deploy.sh` (п. 3, шаг 7) плюс:

```bash
docker ps --filter name=yu-club-                              # 5 контейнеров Up
docker logs yu-club-worker 2>&1 | grep '"msg":"запущен'       # worker стартовал
docker compose --env-file $ROOT/.env -f $ROOT/src/deploy/compose.yml run --rm -T migrate   # «Нечего применять»
```

Ручные, по 17 §17 п.6, на тестовом филиале или тестовом клиенте, в этом порядке: вход сотрудника → расписание открывается, слоты есть → бронь (с сайта по коду и из CRM) → приход → оплата наличными → продажа сертификата и оплата им второго сеанса → баллы начислены (карточка клиента через минуту) → отчёт «Финансы и касса» за сегодня показывает операции → push пришёл подписанному браузеру → ночная сверка вручную без расхождений (`reglament-sboya.md` п. 7).

Сквозной прогон `npm run test:e2e:stand` (`tests/e2e/*.spec.ts`: полный цикл, VR+PS4, деньги Э2, Э3) – **только стенд**: тесты читают код входа клиента из лога API по ssh (`tests/e2e/stand.ts`), создают реальные брони и платежи на демо-филиале, требуют пароли из `~/.config/yu-club`. На бою с SMS-провайдером и без демо-филиала он не применим; боевая проверка – ручная по списку выше.

Через час и на следующее утро: `backup.log` без «ОШИБКА», `/reports/reconcile` чисто, лента событий и журнал уведомлений без массовых «не доставлено».

## 5. Откат

Решение – Владелец по докладу технического администратора. Два сценария.

**А. Откат кода без данных** – миграции релиза совместимы со старым кодом (только добавление таблиц, колонок с умолчанием, представлений, индексов) или релиз без миграций:

```bash
git checkout <предыдущая ревизия>          # из записи о прошлом релизе или $ROOT/src.old/REVISION
deploy/deploy.sh                            # та же процедура, собирает старые образы заново
git checkout main
```

Данные остаются как есть; применённые миграции в `schema_migrations` тоже остаются – старый код их не замечает. `migrate up` при следующей выкладке новой версии снова скажет «Нечего применять».

**Б. Откат с данными** – миграция релиза меняла или удаляла данные, или код после выкладки писал в базу неверно:

1. Остановить `worker site crm api`.
2. Восстановить дамп, сделанный до выкладки (п. 2 шаг 4), по `reglament-sboya.md` п. 6; всё, что ввели после выкладки, пропадает – сотрудников предупредить, бумажный журнал по п. 8 регламента.
3. Выложить предыдущую ревизию (сценарий А).
4. Сверка по `reglament-sboya.md` п. 7.

Команда `node db/migrate.ts down [N]` в раннере есть, но в бою не используется: секция `down` откатывает схему, а не данные, которые новый код успел записать, и часть миграций в `down` только удаляет объекты. Откат схемы = восстановление из дампа до релиза (сценарий Б). Исключение – миграция, применённая на бою по ошибке, под которую код ещё ничего не писал: `down 1` допустим решением техлида, с записью в журнал релиза.

Образы и `src.old` на сервере держат одну версию назад – для отката на две и больше версии нужен git.

## 6. Миграции: правила

Из `db/migrate.ts` и ADR 0001:

- Файл `db/migrations/NNNN_имя.sql` с секциями `-- migrate:up` и `-- migrate:down`; каждая миграция в своей транзакции (`CREATE INDEX CONCURRENTLY` не поддерживается); повторный `up` – no-op; параллельные запуски сериализуются advisory-lock.
- Применённый файл менять нельзя: контрольная сумма не совпадёт, раннер остановится с ошибкой «изменена после применения».
- Порядок строгий: неприменённая миграция с номером меньше последней применённой – ошибка «порядок нарушен». На стенде лечится `--reset-stage`; **на бою запрещено** – перед первым боевым релизом техлид один раз выстраивает миграции 03xx/04xx в окончательном порядке (план 6.5.1, техдолг 1.7), дальше только новые номера.
- Миграции идут под `yu_owner` (`MIGRATION_DATABASE_URL`), рантайм – `yu_app`; `UPDATE`/`DELETE` на журналах у `yu_app` нет.
- В записи о релизе у каждой миграции: номер, что делает, совместима ли со старым кодом, нужен ли откат с данными. Это и есть «план отката для релизов, затрагивающих данные» (18 §15).

## 7. Критерии «стоп»

Выкладка прерывается и запускается откат, если:

- `deploy.sh` завершился с ошибкой на миграциях («порядок нарушен», «изменена после применения», SQL-ошибка) – база в состоянии до упавшей миграции (транзакция), приложение старой версии ещё стоит; ничего не трогать, звать разработку;
- worker не запустился или не написал «запущен»;
- `/health` не отдал новую версию или код не 200;
- Caddy или nginx не приняли конфиг (скрипт сам вернул копию) – соседние сайты проверить;
- коды соседей «до» и «после» различаются;
- ручная проверка п. 4 не прошла на входе, расписании, брони, оплате;
- ночная сверка после выкладки показала расхождения, которых не было накануне;
- бэкап до выкладки не сделан или `restore-check` не прошёл – выкладку вообще не начинать.

## 8. Первая боевая выкладка: отличия от стенда

1. `$ROOT/.env` на боевом сервере создать до первого запуска `deploy.sh` с `APP_ENV=prod` (скрипт сам пишет `APP_ENV=stage`; при `prod` сайт индексируется, демо-засев и коды входа в логе запрещены, вход клиента требует SMS-провайдера – техдолг 1.4, 3.1).
2. Домены и TLS: `YU_DOMAIN`, `YU_CRM_DOMAIN`, `PUBLIC_SITE_URL`; Caddy с настоящим ACME вместо `tls internal` (техдолг 1.3); 301, не 308 (техдолг 1.13).
3. `TRUSTED_PROXIES` под свой обратный прокси (1.6); том медиатеки в Caddy только для чтения (1.9); `UNSUBSCRIBE_SECRET` для рекламы (3.7); `BACKUP_ALERT_URL` (2.3); копия вне сервера в РФ (2.2).
4. Владелец: `docker compose ... run --rm -T --no-deps -e OWNER_EMAIL -e OWNER_PASSWORD api node apps/api/src/modules/staff/seed-owner.ts` (пароль только через окружение, обязательная смена при первом входе). Затем `chek-list-napolneniya.md`.
5. Порядок миграций выстроен (п. 6), в `db/migrations` нет пропусков и дублей, CI на чистой базе зелёный.
6. Прогон восстановления из копии на стенде с замером времени до того, как сервер объявлен боевым (18 §9.2 п.7, `reglament-sboya.md` п. 6).
